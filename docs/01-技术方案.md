# 本地开源投屏工具 —— 技术方案

> 版本：v1.0（草案） 日期：2026-11-22
> 目标：手机投屏到电脑的本地化开源工具，支持投屏码 / 二维码连接，同一局域网内点对点直连。

## 1. 需求拆解

| 需求 | 本质 | 关键约束 |
|---|---|---|
| 手机投屏到电脑 | 手机屏幕画面实时传输到电脑显示 | 低延迟、画面连续 |
| 投屏码 / 二维码连接 | 会话匹配机制，避免手动输入 IP | 码唯一、可复用、即扫即连 |
| 同一局域网 | 点对点直连，不经过公网 | 无需 STUN/TURN 中继，延迟最低 |
| 支持红果、抖音、B站等平台 | 采集方式与目标 App 解耦，平台无感 | 采集权限由系统弹窗授权 |
| 本地使用、开源 | 无云服务依赖，代码可自由分发 | 全部本地化，零外部 CDN 依赖 |

## 2. 技术选型

对比三条路线：

1. **WebRTC 纯浏览器方案（选定 ✅）**
   - 手机 Chrome 打开投屏页 → `getDisplayMedia` 采集屏幕（含红果等任意 App 画面）→ WebRTC 点对点推流 → 电脑端页面播放。
   - 优势：无需安装手机 App、无需 ADB/Root、延迟 100~200ms、码率自适应、代码全开源可控、对 App 平台完全无感。

2. 逆向 AirPlay / Miracast 协议
   - 延迟最低，但协议未公开、实现复杂、仅限特定生态，且无法覆盖红果等国产 App 的内嵌播放，**否决**。

3. 截图 / 录屏轮询
   - 实现简单但延迟高（秒级）、画面卡顿、功耗高，**否决**。

## 3. 系统架构

```
┌─────────────┐   HTTP    ┌─────────────┐
│  手机端页面   │◄────────►│  信令服务     │   (Node.js)
│ (Chrome 打开)│   WebSocket│ HTTP + WS   │
│ 采集屏幕流   │           │ 投屏码匹配    │
└──────┬──────┘           └─────────────┘
       │ WebRTC 媒体流（局域网 P2P 直连，不经过服务端）
       ▼
┌─────────────┐
│  电脑端页面   │  接收并全屏播放
└─────────────┘
```

- **信令服务**（Node.js，端口 8080）：
  - 生成 6 位投屏码，服务端保存会话状态；
  - 为电脑端生成二维码（内容 `http://<电脑局域网IP>:8080/cast?code=XXXXXX`）；
  - 通过 WebSocket 匹配手机端与电脑端，转发 WebRTC 协商消息（SDP offer/answer、ICE candidate）。
- **媒体流**：WebRTC P2P 直连，**不经过服务端**，局域网内延迟与带宽最优。
- **红果适配（第一阶段目标）**：手机在红果 App 内播放视频时，投屏页以 `getDisplayMedia` 采集「整个屏幕」，红果画面原样上屏。采集方式与 App 无关，**天然覆盖抖音、bilibili 等全部平台**，无需针对单个平台做适配。

## 4. 连接流程（时序）

```
电脑端                    信令服务                  手机端
  │ 打开接收页                │                        │
  │──请求投屏码─────────────►│                        │
  │◄──投屏码+二维码DataURL───│                        │
  │ 展示投屏码/二维码          │                        │
  │                          │                        │ 扫码打开 /cast?code=XXXXXX
  │                          │◄─── WS 连接(携带code) ───│
  │                          │ 校验码匹配               │
  │◄────── WS：有设备来投屏 ─│─────── WS：可以投屏 ────►│
  │                          │                        │
  │◄═════ WebRTC 协商（SDP/ICE，经信令转发）═════►│
  │◄════════════ WebRTC 媒体流（P2P 直连）═══════════►│
  │ 接收画面，全屏播放          │                        │ 屏幕采集中
```

1. 电脑端打开接收页 → 信令服务分配 6 位投屏码并返回二维码（DataURL，页面本地渲染，无外部请求）。
2. 手机扫码（微信/相机等任意扫码工具）→ 自动打开投屏页 → 自动携带投屏码建立 WebSocket。
3. 服务端校验投屏码匹配 → 分别通知两端，手机端弹出系统屏幕采集授权。
4. 两端 WebRTC 协商 → 授权通过后画面实时上屏，电脑端可全屏、静音切换。

## 5. 关键设计决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| 投屏码格式 | 6 位数字 | 输入/扫码都方便，空间足够 |
| 二维码生成位置 | 服务端生成 PNG DataURL | 页面零依赖、完全离线可用 |
| WebRTC 编解码 | 浏览器默认（VP8/VP9/H.264） | 无需额外编码库，浏览器原生支持 |
| 信令通道 | WebSocket | 双向、低延迟、与 HTTP 同端口部署 |
| 会话模型 | 一个投屏码对应一次会话，先到先服务 | 简单可靠；多设备扩展留待 v2 |
| 断线处理 | 电脑端断开后投屏码失效，重新打开生成新码 | 防止旧码被误用 |

## 6. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 部分国产手机浏览器不支持 `getDisplayMedia` | 无法采集屏幕 | 页面检测能力并明确提示，建议使用 Chrome |
| 系统录屏授权弹窗被拒 | 无画面 | 页面给出授权引导，拒绝后可重新触发 |
| 路由器 AP 隔离 / 双频路由 2.4G 与 5G 不互通 | 两端连不上 | 两端均有连接超时提示，文档给出排查指引 |
| 本地环境公网 CDN 不稳定 | 页面白屏 | 所有前端资源本地化，零外部依赖 |
| 无 STUN/TURN | 跨网段无法互联 | 本工具定位同局域网，文档明示边界；预留配置项 |

## 8. 范围边界（v0.1）

- **包含**：手机→电脑单向投屏、投屏码+二维码、局域网 P2P、红果验证（架构天然支持全平台）、全屏播放、静音切换、断线提示。
- **不包含**：反向控制（电脑操控手机）、声音投屏、跨网段投屏、一对多投屏、手机端 App 形态。以上列入 v2 候选。
